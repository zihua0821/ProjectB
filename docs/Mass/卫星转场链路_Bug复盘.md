# 卫星转场链路 Bug 复盘（离轨 / 悬停 / 回轨）

> 范围：从"回轨链路调不通"到"离轨/入轨视觉正确"的全过程
> 结论：**8 个缺陷，其中 5 个源于"设计层"（双事实源 / 坐标系混用 / 判据与显示不同源），3 个源于"实现层"（判据常量、控制点、采样密度）**
> 价值：每个缺陷都提炼成一条可复用守则，已回写进需求/执行方案

---

## 一、总览

| # | 现象 | 根因层 | 根因一句话 | 修复 |
|---|---|---|---|---|
| 1 | 回轨绕背面 / 路径穿球 | 实现 | 贝塞尔控制点偏移 `k×|P0P3|` 在远距离转场时被甩飞 | 偏移封顶 `d ≤ 高度差` |
| 2 | 方向判据错（delta=355.1°） | 实现 | 有向夹角的分支写反 | 统一为 `ComputeHoverToSlotSignedAngle` |
| 3 | 选槽成功但永不起飞 | 实现 | 等待判据的两个入参都是**固定值** → δ 恒定 | 改用**槽位实时世界位置** |
| 4 | 青球（槽位）恒定落后卫星 | **设计** | 槽位与卫星是**两条独立推进的相位线**，起点差 → 恒定偏差 | 渲染锚点改用槽位点（方案 B） |
| 5 | 离轨起飞瞬间"回跳一小段" | **设计** | DepartWait 判据用**账面相位**，而显示位置由**槽位**驱动 | 判据改用【实测显示位置】 |
| 6 | 回轨落点比槽位超前 | **设计** | 落点 = `悬停投影 + ωT`，但槽位实际在 `悬停投影 + δ0` | 落点加 **δ0 补偿** |
| 7 | 回轨完成后瞬移 4.6° | **设计** | 到达时清 `槽索引` 但未清 `认领句柄` → 渲染回退到账面相位点 | 单一事实源：删索引，统一按句柄查询 |
| 8 | 两条弧的公共端点 ≠ 悬停点 | **设计** | "悬停点"沿**格子法线**定义，而"轨迹点"被约束在**轨道平面内** | 轨迹增加**垂直分量**（平面内 + 法线偏移） |

**共性**：8 个里 5 个是"**两个来源/两套定义/两条线**"的问题——一旦存在两处事实，就有漂移/不同步的必然性。

## 二、逐个复盘

### Bug 1：回轨绕背面、路径穿球（实现层）

```
现象：卫星从悬停点起飞后绕向"球背面"，中段半径下探穿球
定位：诊断日志打印 P0/P1/P2/P3 与各自 |pos| —— 发现 |P1|/|P2| 远大于 |P0|（控制点被甩出球外）
根因：控制点偏移 d = k × |P0→P3|；当起终点相距很远（跨半球转场）时 d 达数万，
      控制点被拉到球外 → 曲线绕大弧；而"沿切向偏移"还会让控制点半径下降 → 中段穿球
修复：① 偏移封顶 d ≤ 高度差（径向跨度）② P2 改用终点法线（对称于 P1）
教训：**控制点的"相对量"必须相对于"本次任务的实际尺度"做约束**，不能用一个纯比例 k 一路乘下去
（后续整体被"极坐标同步转场"取代，此条已随方案 2 归档）
```

### Bug 2：方向判据写反（实现层）

```
现象：日志出现 delta=355.1°（应为小角度），并伴随"反向飞"
定位：打印"目标方位 / 当前相位 / 有向夹角"三元组，对照运动方向
根因：有向夹角的符号分支（顺时针取反）写在了错误的分支里；
      更糟的是"改对又改错"——因为没有先确认代码约定（谁减谁、以什么为正）
修复：抽出唯一函数 ComputeHoverToSlotSignedAngle（沿运动方向为正，顺时针取反），全文只用它
教训：**方向类判据必须收敛到单一函数**；多写一份就多一处可以写反的地方
```

### Bug 3：选槽成功但永不起飞（实现层）

```
现象：选槽成功（delta=-44.6°），但卫星一直等（dist 从 6577 涨到 91584）
定位：每帧打印"等待判据的输入值"——发现 δ 恒为 −44.6°（一个字节都不动）
根因：等待判据写成 ComputeHoverToSlotSignedAngle(悬停点, Task.PhaseEndLocation)，
      而 PhaseEndLocation 是【选槽时的快照点】——两个入参都是常量 → 结果恒定
修复：等待判据改用【槽位的实时世界位置】；并引入"当前归属槽"的稳定标识（当时是索引）
教训：**"等待/触发"类判据，输入必须包含"随时间变化的那一项"**；
      用日志验证"这个值在变吗"是第一优先动作
```

### Bug 4：青球恒定落后（设计层）

```
现象：槽位球与卫星在轨道上始终差一小段（恒定，约 4.9°）
定位：同时打印"槽位相位"与"卫星相位" —— 两条线各自推进，起点/启动时刻不同 → 恒定偏差
根因：**槽位相位与卫星相位是两条独立推进的线**（不同系统、不同起点），同速但不同相
修复：渲染锚点改为【归属槽世界点】（方案 B："槽位 = 卫星的轨道锚点"），账面相位退居"账目"角色
教训：**同一个物理量不要有两个推进源**；
      "看起来应该一致"的两个量，如果由两处分别累加，就一定会漂移
```

### Bug 5：离轨起飞瞬间"回跳"（设计层）

```
现象：起飞那一刻卫星"往回跳一小段"再沿轨迹飞
定位：打印（账面相位 → 提前量点）的差值 与（显示位置 → 提前量点）的差值，对照后确认两者不同
根因：DepartWait 判据用【账面相位】，而"显示位置"由【槽位】驱动；
      判据在账面上满足时，显示位置其实还差一点未到 → 起飞帧写覆盖 = 位置被改写 → 视觉回跳
修复：① 判据改用"显示位置 ↔ 提前量点"的距离（与渲染同源）
      ② 起点方位也不再"公式反推"，直接取【实测显示位置的方位】——从哪儿起飞就从哪儿算
教训：**判据的参考物，必须与玩家看到的东西同源**；
      "公式算出的位置"与"实际显示的位置"如果不同源，就一定会在某个时刻打架
```

### Bug 6：回轨落点超前（设计层）

```
现象：落点比槽位"超前"一段（约 2~3°，取决于起飞时机）
定位：逐帧打印 delta（槽位相对悬停投影的有向夹角），取触发帧的值；再用"到达方位 = 起点 + ωT"算出偏差
根因：落点定义为"悬停投影 + ω·T"，但槽位起飞时其实在"悬停投影 + δ0"；
      槽位与卫星同速 → 这个 δ0 被"冻结"到落点，永不消散
修复：落点改为"槽位相位 + ω·T"，实现上给切向推进量加 δ0 补偿：
       Δθ = ω·T·dir + δ0（δ0 = 槽位相位 − 悬停投影方位）
教训：**目标物在运动时，"落点"应以【目标的相位】为基准，而不是以【理想几何点】为基准**；
      同速两者之间的任何偏差都会永久保留——必须显式补偿
```

### Bug 7：回轨完成瞬间瞬移 4.6°（设计层）

```
现象：飞行末尾与槽位重合良好（endToSlot=67cm），但"到达清覆盖"的瞬间跳到 4.6° 之外
定位：到达瞬间同时打印三个距离：落点↔槽位 / 落点↔账面相位点 / 槽位↔账面相位点
      → endToSlot=67（好） 但 slotToPhase=4622（差 4.6°）→ 说明"清覆盖后渲染走了另一条分支"
根因：到达分支里清了【槽索引】却保留【认领句柄】→ 渲染逻辑判断"无槽" → 回退用账面相位点 ≠ 槽位
      （本质：同一事实存在两个字段，生命周期不同步）
修复：① frag 只保留认领句柄（删掉槽索引）
      ② 槽位查询统一走"按认领句柄"（GetOrbitSlot*ByClaim，内部反查索引）
      ③ 到达时把账面相位对齐槽位（双保险）
教训：**同一事实只留一个字段**；
      如果为了"方便"同时维护"索引 + 句柄"，就要接受"两者可能不同步"这种缺陷的存在
```

### Bug 8：两条弧的公共端点 ≠ 悬停点（设计层）

```
现象：离轨终点与回轨起点接得上，但都与"悬停点"差一段（测试格"悬停点更偏上"）
定位：把两个点分别代入定义 —— 悬停点：格子法线 × (R_planet + h)；轨迹点：轨道平面内 (θ, r)
      → 半径相同、方向不同（一个在平面外，一个被平面约束）
根因：**两个几何定义各自成立，但不在同一个坐标系/子空间内**；
      当格子不在轨道平面正对处（服务距离越远越明显）时，偏差越大
修复：轨迹改为"平面内 + 法线偏移"两分量：
       pos(α) = ComputeOrbitWorldPosition(r(α), θ(α)) + n × v(α)
       · 离轨 v: 0 → d_hover；回轨 v: d_hover → 0
       · 增量：DecomposeToOrbitPlane(点) → (θ, r, v)；frag 增 PhaseVerticalStart/End；T 用合成跨度
教训：**"点"必须明确属于哪个子空间**；
      跨子空间的两个定义（"格子上方" vs "轨道平面内"）不能混用——要么统一，要么显式补维度
```

## 三、方法论沉淀（怎么更快定位下一类问题）

### 1. 诊断日志三原则
```
① 【每帧】关键判据（等待/触发类）不要节流——节流会让你永远错过"触发那一帧"
② 【打印输入而非结论】打印"判据的每个入参"，而不是只打"触发/未触发"
③ 【同帧对照】把"疑似不同源的两个量"放在同一行打印（账面 vs 显示、落点 vs 槽位 …）
```

### 2. 定位顺序（本次实践有效）
```
① 先从"数据"确认现象（贴日志/打印关键量）——不猜
② 确认"这个值在变吗" → 不变 = 常量/固定值 bug
③ 确认"判据的参考物，与显示是否同源"
④ 确认"两个量是否由两处分别维护"（双事实源）
⑤ 确认"两个点是否在同一子空间"
（顺序即：常量 → 同源 → 单一事实 → 坐标系）
```

### 3. 设计复核清单（写方案时自查）
```
□ 这个物理量有几个推进源？（>1 就会漂移）
□ 这个事实存了几个字段？（>1 就会不同步）
□ 判据看的量 = 玩家看到的量吗？
□ 目标在运动时，落点用了"目标的相位"还是"理想几何点"？
□ 涉及的"点"定义在哪个子空间？跨子空间的地方补维度了吗？
□ 控制点/偏移量这类"相对量"，是否相对于本次任务的实际尺度做了约束？
□ 方向类符号判据，是否只有一处实现？
```

### 4. 与"方案 2（极坐标同步转场）"的关系
```
本次 8 个缺陷里，Bug 1/2/3 属于"贝塞尔追运动目标"路线的固有问题
（移动目标 + 定点曲线 → 必须预测/动态改终点 → 各种别扭）
方案 2 直接以"切向 ω 同步 + 径向匀速"构造轨迹，一次性消掉：
  · 不需要预测（同步即预测）
  · 不需要相对量约束（半径/方位都是绝对量插值）
  · 不需要方向判据（θ 单调推进）
→ 教训：**当"实现层修修补补超过 3 次还不好"时，回头质疑"任务与工具的匹配性"**
   （贝塞尔是"定点→定点"的工具，被用来追"运动点"；这就是任务错配）
```

## 四、代码侧成果（本次留下的"结构化改进"）

| 项 | 说明 |
|---|---|
| `DecomposeToOrbitPlane` | 空间点 → （平面内方位/半径 + 法线偏移）；跨子空间问题的统一解 |
| 轨迹两分量模型 | `pos = 平面内(θ, r) + n × v`；端点由构造精确命中权威点（悬停点） |
| `ComputeHoverToSlotSignedAngle` | 唯一方向判据函数（沿运动方向为正） |
| `GetOrbitSlot*ByClaim` | 按认领句柄查询槽位（内部反查索引）；消除"索引+句柄"双字段 |
| δ0 补偿 | 落点 = 目标（槽位）相位 + ωT；同速偏差显式补偿 |
| 单一事实源 | frag 只留认领句柄；槽位/落子/渲染锚点全部走同一句柄 |
