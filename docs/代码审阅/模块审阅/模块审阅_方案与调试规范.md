## 一、背景与目标

```
时间线审阅（已完成、已归档）：回答"代码是怎么长出来的"——按提交演进，纵向 diff 视角，
  收获 = 演化史（每个决策的来源、踩过的坑、缺陷复盘）+ 全八阶段与 HEAD 合龙。
遗留落差：任何一轮都没有"把一个文件从第一行读到最后一行的完整体验"——
  终态代码的结构、数据流、调用链没有被系统走过一遍 → 掌控感不足。

模块审阅（本阶段）：回答"现在是什么、实际怎么跑"——按当前模块结构横向走读终态源码，
  静态导读（结构/数据流/调用链）× 动态断点走查（真实时序/数据实值）双轨对账。
```

**目标**：
1. **结构掌握**：每个模块的职责边界、数据结构、调用链能自述（可讲、改代码有底）；
2. **运行验证**：关键链路的"代码应该怎么走"与"实际怎么走"完成对账（断点走查）；
3. **副产品**：走读中发现的注释问题收集入主清单 §七 池（为注释统一修订阶段备料）；对照修正三份现存技术文档。

**与后续阶段的关系**：
```
模块审阅（本阶段）→ 注释统一修订【✅ 已完成（10-13）】→ EQS 回归（N3）
```

## 三、每模块三步闭环

```
① 静态导读（AI 产出《导读》文档）
   · 文件清单与入口：本模块包含哪些文件，各从哪开始读
   · 结构/职责：类/结构体的职责边界与关键字段（字段 → 谁写 → 谁读）
   · 数据流：数据在模块内的产生 → 流动 → 消费（含跨模块流入流出的锚点）
   · 调用链：主链路 + 关键分支（含跨模块调用的衔接点）
   · 断点地图：该模块值得断的关键函数清单（见 4.2 规范）
   · 自查清单：用户对照代码走读时的勾选点（"看到 X 应理解 Y"）

② 动态走查（用户主导 + AI 辅助，见 4.3 操作流程）
   · 按断点地图逐点走查：真实运行时序、数据实值、分支走向
   · 走查中"代码与理解不符"之处当场讨论

③ 答疑落档
   · 走查发现记入《导读》文档尾部（"走查记录"节）
   · 注释问题 → 主清单 §七 池；代码问题 → 评估（走批流程）
   · 用户确认"掌握" → 更新进度表 → 下一模块

④ 模块收口修订（2026-10-06 用户定：修订节奏）
   · 本模块审阅完成（用户意见集齐）→ 集中实施本模块裁决的代码修改（一模块一收口，不跨模块攒批）
   · 修改当前模块文件后即时 reindex（逐文件）；编译验证由用户执行
   · 修订完成 → 下一模块
```

## 四、调试细节规范（断点走查）

### 4.1 工具链（均已验证可用）

```
调试器（jetbrains-rider · xdebug_*）：
  xdebug_set_breakpoint / xdebug_remove_breakpoint / xdebug_list_breakpoints —— 断点增删查
  xdebug_control_session —— 会话（resume/pause/stop）
  xdebug_get_debugger_status —— 命中状态确认
  xdebug_get_threads / xdebug_get_stack —— 线程与调用栈（"我怎么到这里的"）
  xdebug_get_frame_values / xdebug_get_value_by_path —— 帧内变量/深层字段（指针链、容器元素）
  xdebug_evaluate_expression —— 任意表达式求值（公式现场验证，如相位差计算）
  xdebug_run_to_line —— 临时"跑到某行"（不设永久断点）
运行与画面（jetbrains-rider · ue_*）：
  ue_health —— 前提检查（RiderLink 连接）；ue_status —— playState 确认
  ue_play —— PIE 可控启动/停止；take_screenshot —— 命中断点时画面定格截图（数据↔画面对账）
  ue_get_logs —— 日志辅助
日志（既有基建）：
  变化驱动日志（低频打印状态变化）；探针（Verbose，排查时开）；[SatelliteTask]/[OrbitPlan] 功能日志
前提：游戏以调试配置运行（Rider 调试会话可用断点）；调试会话配置 configurationName='ProjectB'
```

### 4.2 断点地图规范（导读文档内的表格）

导读中每个候选断点一行：

```
| 函数（文件:行） | 触及时机 | 观察到什么 | 重点变量 | 线程 | 频率 |
|---|---|---|---|---|---|
| DispatchOrbitPlan（Manager.cpp） | 发单瞬间（漂移/落座） | 目标槽选择结果 | TargetSlotIndex/OldHandle/NewHandle | GT | 低频（1s 节拍内触发时） |
```

**选取原则**：
- **低频关键点优先**：创建/重建、发单、中断、到达、认领切换、状态转移瞬间（单次或秒级）；
- **数据转折点优先**："值被改写的那一行"（句柄切换、相位重写、覆盖写入）比"路过点"有价值；
- **高频点（每帧执行）不设裸断点**：改用条件断点（如"仅当实体 Index==N"）或退化到变化驱动日志；
- 每轮走查控制在 **3~6 个断点**（走查是精读，不是全测）。

### 4.3 走查操作流程（标准序列——AI 全托管备选版；默认模式见 4.6）

```
1. 前置：ue_health 检查连接；确认游戏/编辑器状态（ue_status；必要时 ue_play 启动 PIE）
2. 设点：AI 按断点地图 xdebug_set_breakpoint（文件+行号）——一次不超过 2~3 个
3. 触发：用户操作游戏（种地/等待漂移/改轨道参数等）；AI 不代操作游戏内动作
4. 命中：xdebug_get_debugger_status 确认 → 通知用户"已停在 X"
5. 观察（AI 收集数据包，一屏汇报）：
   · xdebug_get_threads → 确认在 GT 还是 worker
   · xdebug_get_stack → 调用链（"从哪条链走进来的"——与导读调用链对账）
   · xdebug_get_frame_values / xdebug_get_value_by_path → 关键变量实值
   · xdebug_evaluate_expression → 现场算公式（如 δ0 = FindDelta(Slot, Hover)）
   · take_screenshot → 定格画面（视觉 ↔ 数据对账）
6. 讨论：数据与导读预期对照——不符处标记（是理解偏差 or 代码事实）
7. 放行：xdebug_control_session（resume）——继续或移除该断点换下一个
8. 记录：填《导读》尾部的"走查记录"节（断点/时机/实际值/对账结论）
```

### 4.4 线程与框架注意事项

```
· GT 断点（任务链/管理器/规划器/SlotSync）：整帧冻结——最安全，画面静止对照数据
· worker 断点（Movement=SatelliteMovement、Plan=SatellitePlan 处理器）：该线程挂起，
  Mass 帧序等待——观察完尽快放行，避免长时间停住造成下游超时观感
· Mass StateTree【资产内】断点（资产图节点上的断点）：历史体验为"未按预期命中/行为异常"，
  当时权宜结论"改用变化驱动日志"。归因不武断——可能是操作方式（如调试会话附着、
  实例化上下文、Schema 节点映射）也可能是引擎机制，【列入 M-1 轮专项验证】：
  用户准备好复现条件时，用最小场景（单星）专门验证一次，再下结论。
  注：C++ 侧断点（任务类成员函数、处理器、组件）不受此影响，为常规手段。
· 条件断点：优先用 xdebug 的条件能力或"断点 + 快速过滤"控制命中（高频函数必用）
· 断点清理：每轮走查结束 xdebug_list_breakpoints 确认清空，防残留断点跑偏后续验证
```

### 4.5 数据观察四通道（互为交叉验证）

```
① 调用栈 —— "谁调用的"（时序与来源）
② 变量/求值 —— "值是多少"（数据实值；公式现场复算）
③ 画面截图 —— "玩家看到什么"（视觉与数据对账——尤其转场/漂移瞬间）
④ 日志 —— "历史序列"（断点看不到的"之前发生过什么"；变化驱动日志补时序）
```

### 4.6 走查模式（2026-10-06 修订：用户自主 + AI 协助）

```
【默认模式】用户在 Rider 里自主断点走查（按本模块《导读》断点地图）：
· 会话建立：AI 代 attach（编辑器运行中）或用户在 Rider 里自行配置；
· 用户主导：自行设点/触发/看栈与变量/单步——数据一眼即见，无需往返；
· AI 协助：① 断点地图行号维护与校准（代码变动后）② 对账与答疑（用户口述实际值/贴截图 →
  AI 对照导读预期）③ 走查记录汇总落档 ④ 窄查询（仅当用户点名某表达式时才 evaluate 单个值，
  避免全量线程表/栈/变量大树——节省往返与 token）。
【反馈约定】口头结论优先（“符合预期”/“值不对，是 YY”）；截图其次（Rider 变量面板/画面）；
AI 数据拉取仅限窄问题。
【备选模式】“AI 全托管走查”（4.3 八步序列：AI 设点/收数据包/汇报）——仅在用户明确要求时启用。
【按需口径（10-09 定）】断点走查按需进行：用户可裁定“不做”（静态审阅完成即可）——
导读“走查记录”节注明口径（不保留空表）；进度表“走查”列如实标记（✅=做过 / —=未做）。
```
