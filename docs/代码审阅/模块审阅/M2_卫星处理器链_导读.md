## 二、帧序链（"后继声明前驱"的单向声明体系）

```
SatellitePlan ──▶ SatelliteSlot ──▶ SatelliteMovement ──▶ SatelliteRender ──▶ SatelliteHeartbeat
  (worker)          (GT)              (worker)              (GT)                (并行收集→信号)
  1s 节拍            槽推进             相位推进               渲染同步              发心跳信号
     │                 │                  │                    │                    │
  抄账/求解/发单    UpdateOrbitSlots    纯 VirtualPhase       位置三优先级         SignalEntities
  （写句柄/请求/覆盖） （槽相位+位置缓存）  （+ω·dt·dir）        → ISM 批提交        → 引擎 StateTree 处理器（GT）
                                                                                        └─▶ M-1 任务链 Tick
```

**设计要点**：
- 单向链：每个处理器只声明"我在谁之后"（ExecuteAfter 前驱名）——调整顺序只改一处；
- 先槽后星：Slot 在 Movement 前（M1 裁决——原来槽推进寄生在 Movement 内，竞态+越权）；
- 渲染最末：Render 在 Movement 后（同帧读到最新相位与同帧槽缓存——"渲染总是最新"）；
- 心跳压轴：所有数据就绪后才发任务信号（任务看到的是本帧终态）。

## 三、各处理器职责明细

### 3.1 Plan（worker）——规划节拍驱动
```
Execute（L26-46）：暂停宏 L29 → 首 chunk 执行一次 L32-39 → Shared.SatelliteManager->TickOrbitPlanning()（L43）
内含（在 M-3 展开）：1s 节流 → CollectOrbitSnapshots → BuildOrbitPlan（纯函数）→ DispatchOrbitPlan（写 fragment 三件套）
读：ConstShared（Manager 指针）　写：fragment（SlotClaimHandle / bDriftRequested / OverrideLocation）
走查关注：worker 访问面与 L15-16 注释声明的一致性（M1 裁决落地点——只读稳定数据 + 引擎允许调用 + 自用节流）
```

### 3.2 Slot（GT）——槽位推进（M1 新增的专职处理器）
```
Execute（L26-48）：暂停宏 L29 → 首 chunk 执行一次 L34-41（GT 单线程，无竞态）
→ Shared.SmartObjectManager->UpdateOrbitSlots(dt)（L45）——槽相位/世界位置缓存 + DrawDebug
读：ConstShared（Manager 指针）　写：组件内部缓存（M-4 展开）
```

### 3.3 Movement（worker）——纯相位推进
```
Execute（L52-70）：暂停宏 L55 → 逐 chunk 逐实体 UpdateOrbitPhase（辅助函数 L15-31）
UpdateOrbitPhase：ω≈0 早退（L17-20）→ VirtualPhase += (±1)·ω·dt（L22）→ 归一化 [0,360)（L24-29）
读/写：仅 FMassSatelliteOrbitFragment（worker 并行安全——不再触碰任何 UObject）
```

### 3.4 Render（GT）——位置→ISM 渲染同步
```
Execute（L30-85）：逐 chunk 收集（L37-75）→ 末尾一次 BatchUpdateInstancesTransforms（L82-84，bTeleport）
位置优先级（L57-70）：
  ① OverrideLocation（覆盖：飞行/作业）        ← M-1 的覆盖位置流
  ② GetOrbitSlotWorldPositionByClaim（槽世界点）← M-4 的槽缓存（同帧最新）
  ③ ComputeOrbitWorldPosition（相位现算）      ← 无槽兜底（"总是像正常卫星"）
跳过：InstanceId 无效的实体（L52-55——防"未注册就渲染"）
```

### 3.5 Heartbeat（并行收集）——任务心跳
```
Execute（L28-55）：暂停宏 L31 → 收集全部卫星实体（chunk 并行 + FCriticalSection 合并，L34-45）
→ SignalSubsystem.SignalEntities(NewStateTreeTaskRequired, 全量)（L54）
作用：给"持续 Running 的树"续命（P2 讨论：引擎对非 Running 树自我补信号；本心跳管 Running 树）
下游：UMassStateTreeProcessor（引擎, GT）响应信号 → M-1 六任务 Tick
```

### 3.6 暂停白名单（编辑模式冻结范围）
```
宏：SIMULATION_PAUSE_RETURN(World)（SimulationControlSubsystem.h L44——当前世界暂停则直接 return）
挂载 5 处：Plan L29 / Slot L29 / Movement L55 / Heartbeat L31 / CropGrowth L30
不在白名单：Render（暂停中继续按静止位置刷新 ISM——无害）；任务链（信号停发即静默）

## 附：静态审阅讨论（10-06）

### S1 槽位推进为什么必须在 GT？（用户质疑 → 核实）

```
用户观察（对的部分）：槽推进没有真正动智能对象——引擎 SmartObject 槽位 FWorldLocation 是静态的
（无运行时位置修改 API），槽世界位置只是本组件自算的平行缓存（代码注释 L457-459 已写明）。
从数据语义看它确实是“纯数学”。

但线程归属红线是“数据驻留地”而非“计算性质”——UpdateOrbitSlots 触碰三样：
· OrbitSlots TMap（CurrentPhaseDeg / SlotWorldPositions）= UObject（组件）成员
  → Mass worker 访问 UObject 数据 = 线程纪律红线（T2 本源：“引擎 Traits 体系不覆盖项目组件”，
    无官方线程安全声明 → 默认 GT-only）
· DrawDebugSphere（L470-474 每槽一球）→ 官方要求 GT（写引擎调试绘制数据）
  ——即使数据搬家，此行仍要 GT 或加守卫
· 读者横跨两线程：任务链（GT·ByClaim）/ 规划快照（worker·GetOrbitSlotPhase）/ 认领（GT）
  → 写者在 worker = 无保护写者 vs 双线程读者

历史闭环：该逻辑原寄生 Movement（worker）chunk lambda（T1 竞态 + T2 违规双犯）→
M1 拆为专职 GT 处理器（修复原则“能不在 GT 就不在 GT——只把必须 GT 的最小部分移出”）。
裁决线：读类访问留 worker（Plan 先例）/ 写类访问（槽推进）必须 GT。

若未来想挪回 worker 的前置：① 槽数据从 UObject 迁至 fragment/shared fragment；
② 查询面全改数据源 + 认领仍往返 UObject（MarkSlotAsClaimed 必须 GT）；③ DrawDebug 拆分。
收益评估：每帧一次 O(槽数) 数学（3 轨×50 槽=150 次向量运算）→ GT 占用微乎其微，搬迁收益≈0。
结论：GT = 数据归属决定的必然（非“保险起见”）；此观察沉淀为 N4 Mass 化候选知识
（“槽位数据 UObject 驻留”= 未来 Mass 化的搬迁对象）。
```

### S2 为什么必须收编进 Mass 帧序，而不是组件 Tick？（用户质疑 → 历史还原）

```
出处：运行期复盘 #10/#11（交接文档易错点 #16 的案例源；用户“好像提到过”——记忆准确）。

| #10 | 卫星与槽位显示错位 ~ω×Δt | 槽推进（组件 Tick）与渲染同步（Mass 帧序）先后不定 |
| #11 | 规划器驱动时序不可控（抄账时点不定） | 组件 Tick 与 Mass 帧序相对位置未约定 |
根因一句话：三驱动源（组件 Tick / Mass 处理器 / 状态树）碰同一批数据，相对顺序无约定。

#10 错位机制：同一帧内谁先跑无约定——渲染先跑用旧槽位置、推进先跑用新位置，
两种结果差 ~ω×Δt，逐帧随机 → 卫星与槽位球恒定错位。

为什么组件 Tick 做不到排序：
· 组件 Tick = UE Actor Tick 机制——排序粒度只有粗粒度 TickGroup，项目无法声明
  它与 Mass ProcessingPhase 的相对位置；
· Mass 帧序 = 声明式依赖图（ExecuteInGroup + ExecuteAfter/Before）——顺序确定、可读；
· 领悟：不对齐两张时刻表（做不到），而是【把动作合并到一张表上】——
  所有运行时驱动收编进 Mass 帧序。

收编后帧序链设计要点的由来：
· 渲染最末（Render 在 Slot/Movement 后）→ 同帧读到最新槽缓存与相位（#10 根治）；
· 心跳压轴 → 任务链看到的总是“本帧终态”；
· 单一暂停机制：白名单 5 处全在 Mass 帧序内（无需为组件 Tick 维护第二套暂停逻辑）。

现状落地（10-06 验证）：SatelliteManagerComponent bCanEverTick=false；
SmartObjectManagerComponent TickComponent 仅剩“分批注册”（注册完空转，L104 注释明示
“槽位推进由专职 GT 处理器在 Mass 帧序内驱动”）。

沉淀：易错点 #16 + 复盘方法论第 4 条“驱动源统一：跨子系统碰数据前，先在“一个帧序”内约定相对位置”。
```

### S3 “纯计算模拟智能对象”是否应改为 Actor 载体旋转？（用户质疑 → 引擎源码核查）

```
用户直觉：槽位推进是自算缓存，不如“附加到 Actor 旋转”——引擎认知静态 vs 项目认知动态，
分裂点客观存在。本次引擎源码核查两大发现：

【发现 1·注释失准】引擎有运行时移动智能对象的公开 API：
  USmartObjectSubsystem::UpdateSmartObjectTransform(Handle, NewTransform)
  ——SmartObjectSubsystem.h L487-493（public 区，非蓝图）；实现 .cpp L343-375
  （空间分区 Remove → SetTransform → Bounds 重算 → 重注册）。
  → 项目注释（SmartObjectManagerComponent.cpp L457-459）“引擎智能对象实例位置不开放运行时修改”
    【不准确】——已登记主清单 §七 注释修订池。

【发现 2·位置派生机制】槽位世界位置 = 实例 Transform × 槽静态偏移：
  GetSlotLocation（.cpp L1452）：SmartObjectRuntime->Transform.TransformPosition(Slot->Offset)。
  实例 Transform 一动，引擎侧全部槽位位置自动派生；GetSlotLocation/GetSlotTransform 读取面齐全。

“Actor 载体旋转”可行性核查：
· 项目现状 = 每槽一个动态实例（RegisterSingleOrbitSlots 循环 CreateSmartObject；N=星数×K）；
· 动态实例 = 纯运行时数据（FSmartObjectRuntime）——【无场景节点，无法 attach】；
· 要用 Actor 载体必须整体换“每槽一个 USmartObjectComponent 挂轨道 Actor”的组件式——
  Actor 生命周期 + N 组件管理 + 重建链大改，且旋转驱动仍要进 Mass 帧序（S2 同款问题）。

为何“引擎权威位置”在当前是负收益（消费模式不匹配）：
· 项目读取：高频（每帧每星）/批量/跨线程（worker 规划快照）→ 数组直索引；
· 引擎 API：按句柄单查 + UObject 子系统访问（worker 读不了）+ 每帧移动触发空间分区 Remove/Add；
· Mass 线程模型要求 worker 可读数据在项目侧 → 缓存副本不可避免（引擎同步后仍要副本=双源回归）。
· 且“引擎位置正确”当前消费方为零：认领只依赖句柄；渲染/判据/快照全走项目缓存。

定性结论：现状不是“模拟”，而是【项目侧高速数据副本】——引擎位置=冷数据（无消费方），
项目缓存=热数据（每帧批量跨线程）。未来触发点：若出现“引擎级空间查询轨道槽”需求
（FindSmartObjects 找最近可用槽/调试可视化需正确位置）→ 评估轻量版：
【单实例多槽 + 每帧一次 UpdateSmartObjectTransform】（每轨一次分区更新，成本可控）。

【证据链补强（10-06 二轮·引擎源码实证）】
事实 2（成本·操作级拆解——全部源码核实）：单次 UpdateSmartObjectTransform（.cpp L343-375）：
  ① TMap 查找（L345）② FInstancedStruct 访问+类型校验（HashGrid.cpp L19）③ TSet<FCell> 哈希查找（HashGrid2D.h L570）
  ④ 链表遍历 O(k) ⑤ Items.RemoveAtUninitialized = TSparseArray freelist 回收【O(1) 不搬运】(SparseArray.h L366)
  ⑥ 父层计数（2层网=1次）⑦ SetTransform=纯成员赋值（Runtime.h L373）⑧ FBox 8 顶点变换
  ⑨ CalcCellLocation（浮点 ≤2 层递进 L504）⑩ TSparseArray 分配 ⑪ FindOrAddCell×2
  ⑫ FInstancedStruct 同类型=原位拷贝【无堆分配】（InstancedStruct.cpp L66-81）⑬ 调试标脏（仅 DEBUG_DRAWING）。
  关键修正：无 O(n) 搬运、无每帧堆分配、无隐藏炸弹——但 ~4-6 次哈希容器操作 + FBox 变换。
  估算 ~0.3–1 μs/次（基于操作估算，非 profiling）：3轨30星(450/帧)~0.15–0.45ms；满配(1000/帧)~0.3–1.0ms
  ——16.6ms 预算的 2–6%（均 GT）+ 空间分区抖动（450-1000 次/帧格子进出）。
  可接受性：现结构下“不致命但不便宜”（对纯真实性收益偏贵）；单实例多槽（1次/轨）=微秒级完全可接受
  ——但需动态 Definition + 重建链全改（便宜的性能路径需贵的工程）。
事实 3（收益·架构裁定——不用“没人读”回避，用户方法论纠正）：
  · 项目唯一运动状态=相位；位置=f(几何,相位)【纯函数派生】——引擎实例 Transform 对项目=未使用的协议字段
    （非“第二份事实”；类比槽定义静态 Offset 也是位置字段）；权威唯一→无功能缺陷。
  · “引擎位置正确”的收益=纯真实性（工具可见性）；空间查询模式与乙案落座（离散席位决定论）不同构
    ——是设计不同构，不是未来会补的空白。
  · 判定标准：位置权威归属取决于“谁消费位置”——全在项目→权威=相位（现状自洽）。
  · 裁定：当前不做（依据=权威唯一+消费不同构+位置派生物——非“没人读”）；未来真实出现引擎侧消费时
    以形态 C（写同步读不变）最小引入，极致需求再评估形态 B（单实例多槽）。
  · 附带修正：引擎 trait 声明 TMassExternalSubsystemTraits<USmartObjectSubsystem> GameThreadOnly=false
    （MassGameplayExternalTraits.h L16）——“worker 绝不能访问”的说法不准确（引擎允许；但无 ThreadSafeRead 显式声明，
    并发安全取决于用法模式——引擎自己在 worker 做只读空间查询）。
本质：槽位=数学抽象（相位为唯一真相），智能对象实例=认领协议载体（句柄容器）——位置对认领无意义。
```

### S4 从需求回看：槽位用智能对象本身是否合理？（用户质疑 → 再评估）

```
用户需求定义（准确）：① 随轨道移动的槽位概念 ② 占有/释放——其他智能对象功能均未用。

当初决策（有案可查）：离轨作业需求方案 §12.6——“自建槽位（int32 索引+自写查询）方案已否决：
两套认领语义并存，无收益”——背景：K=1 时代（每轨 10-20 槽）、复用现有 API“零新写”。

依赖精确清点（本次核实·比预期更浅）：
· 用：Create/DestroySmartObject + MarkSlotAsClaimed/Free（4 API）+ FSmartObjectClaimHandle（类型）
· 未用：空间查询（运行时零调用）/行为定义/启停/荷载/条件系统/引擎位置
· 验证：仅句柄 .IsValid() 字段检查（全项目无引擎验证调用、无账本对比）
· 注册链额外绕弯：每槽 CreateSmartObject + FindSmartObjects 微查询捕获（L375-403）
· 规模：K=5 后每轨 250 个 UObject 级实例（FSmartObjectRuntime：Slots/Tags/条件状态/InstancedStruct）

三个环境变化（为何现在值得重审）：
① 规模 ×5（K=5 扩容：10-20/轨 → 250/轨）
② 位置语义认知（S3）：引擎位置“撒谎”/移动成本/真实性议题——自建无此负担
③ 功能面认知：空间查询与乙案落座不同构（永不使用）——“零新写”省下的开发量，
   现以“100% 协议负担承担 5% 使用面”偿付

自建形态（如果做）：轻量槽池（相位缓存+状态位数组+代际计数）+ 结构化句柄（OrbitRef+Index+Generation；

收益：删除全部引擎依赖（4 API+250 实例/轨+微查询+资产要求）、注册链 μs 级、重建链=清空+代际++、

判定：成立——需求匹配度（架构第一原则）视角下：格子（真用：空间注册/荷载/行为/启停）与
轨道（只用状态机）需求不同构——“两套语义并存”是需求差异的客观映射，非缺陷；
且现状已是“半自建”（位置/相位/推进全在项目侧）——重构只是把最后的状态机收回来。

处置：登记新议题 N8（去智能对象化·自建轻量槽池）——按流程立项（需求/执行方案+用户发起）；
边界：格子智能对象保留（零改动）；叙事升级：从“统一智能对象”到“按需求匹配分层选型”。

【两问补充（10-06）】
问题 1：自建后槽推进的位置是否有变化？
· 帧序定位：基本不变——仍在 GT、仍在 Plan→Slot→Movement 同一节点。GT 约束与智能对象无关：
  ① DrawDebugSphere 要求 GT；② 组件（UObject）数据在 worker 写的纪律（自建后数据仍在组件）；

### S5 “槽推进压缩合并到其他步骤”的可行性评估（用户提议 → 评估后不建议）

```
前提矫正：“自建后无强制线程约束”——基本形态下【不成立】：仍受两条 GT 约束（均与智能对象无关）：
  ① DrawDebugSphere 要求 GT；② 组件（UObject）数据写入纪律 + worker 读者（规划快照）同序。
  自建不解除 GT——若需彻底解约束，更符合引擎范式的路径是“子系统化+并发安全设计”（Crowd 先例，
  见 S6）而非 Mass 化；但收益仍小（μs 级），不值得为此改。

合并可行性（假设约束解除，或同为 GT 也可合并——唯一合理去处 = Render 处理器）：
· 数据流验证：槽推进放 Render 开头——渲染读“槽点”在推进后（同帧最新）✓；
  “先槽后星”→“先星后槽”顺序可互换（Movement 不读槽/Plan 读上帧末值/任务链读本帧终态）✓
· 三个必补的坑：① 暂停白名单——Render 不在白名单，槽推进进 Render 后编辑暂停时
  槽位继续推进+卫星冻结 → 渲染优先级②让卫星显示跟着槽点动（暂停中“在动”）——
  必须加局部暂停检查；② 首 chunk 模式共存（Render 逐 chunk 收集 + 槽推进首 chunk 一次）；
  ③ 帧序可见性丧失（“先槽后星”藏进 Render 内部）
· 收益 vs 代价：收益 = 省一个处理器调度（~μs 级，可忽略）；代价 = 三坑补丁 + 职责混合 +
  M-1 裁决逆转——判定【不划算，不建议】。

正确的优化靶点：
  ① DrawDebugSphere 开关化（每帧 100-250 球绘制开销——量级远大于处理器调度；
     【已列入优化计划·10-06 用户确认】——交接文档 §七；若 N8 立项则槽位球部分随 N8 合并）；
  ② 槽推进本体已 O(N) 最简，无优化空间；
  ③ 根本性线程解放需“子系统化+并发安全设计”（Crowd 先例——共享资源表保持中心化；
     Mass 化形态经评估不取，见 S6）。

原则：处理器数量不是优化目标——一个处理器 = 帧序图上一段可见的时序语义；
调度开销微乎其微，“职责边界的可见性”才是贵的东西——合并需“合并后更清晰”的理由，
此处恰相反。现状独立 Slot 处理器 = M1 权衡后的“最小 GT 单元”——已是优化后形态。
```

### S6 轨道槽 Mass 化评估（用户提问 → 评估后不取）

```
形态澄清：A 槽池实体（每轨一实体+池 fragment）；B 去中心化（无池，占用=各星归约，找空槽扫同轨）；
  C 无状态化（槽相位=纯时间函数现算——非 Mass 化，但同轴问题）

技术事实（引擎源码核实）：
· fragment 可带定长内联数组（先例 FMassNavigationEdgesFragment：TArray+TFixedAllocator<8>）——位图可进
· 但位置缓存（N×FVector ≈ 6KB）不适合 fragment（chunk 内存模型）——Mass 化必须位置现算（读者全改）
· 【决定性对照】引擎自己的 MassCrowd 把 Lane（共享资源表）放在 UMassCrowdSubsystem（UObject 子系统），
  实体只带 LaneHandle（BuildLaneData/GetCrowdLaneData/GetMutableCrowdLaneData…）；且 Crowd 子系统 trait
  GameThreadOnly=false（引擎允许 worker 访问，子系统自理并发）
  → 引擎的答案：共享资源表保持中心化，实体持句柄——不强行 Mass 化；
    项目现状（卫星持句柄→管理器资源表）与 Crowd 形态完全同构——已是在范例形态上

合理性：低——逆引擎最佳实践（共享资源不 Mass 化）+ 范式摩擦（共享可变状态 vs Mass 无共享哲学）；
  线程解放收益微小（S5：μs 级）；形态 B 读放大（O(N) 归约）且“轨道”管理级概念去中心化不彻底；
  形态 C 需时间源/基准重置管理（暂停/编辑）——全链语义替换，同样不划算
成本：大——数据域迁移+实体生命周期（挂重建链）+位置现算+句柄代际+DrawDebug 搬迁
与 N8 的关系：替代终态而非先后步骤（定 Mass 化则 N8 组件自建多余）——应同一次决策二选一
判定：不取——N8 基本形态（组件纯数据）即引擎范式内正解；若要彻底解线程约束，范式路径是
  “子系统化+并发安全”（Crowd 先例）而非 Mass 化——但收益仍小，不值得为此改。
```

### S7 优化模式参照：GT 处理器内部并行化（用户经验 → 适用性评估）

```
模式（项目样板：UCropVisualSyncProcessor，农作物渲染处理器）四要素：
  ① 处理器保持 GT（bRequiresGameThreadExecution=true——UObject 系统访问仍在 GT 单线程）
  ② 循环用 ParallelForEachEntityChunk（chunk 级并行到 worker）
  ③ 并行区内：只碰 fragment + chunk 局部缓冲（TMap/TArray 私有）；跨 chunk 合并用
     FCriticalSection 锁保护
  ④ 并行区外（GT 单线程）：批量提交（ISMManager BatchAdd/BatchRemove）——所有 UObject 操作外移

卫星链适用性评估（逐一核对）：
· Heartbeat（StateTreeTickProcessor）：【已用同款模式】（chunk 并行 + 锁合并收集实体）
· Movement（OrbitMovementProcessor）：循环体【纯 fragment】（写各实体 VirtualPhase）——可换
  ParallelForEachEntityChunk（线程安全天然成立）——一行改动
· Render（RenderSyncProcessor）：循环体内含 UObject 调用（槽点查询）——需快照化改造后换
  【用户决策（10-07）：做得——“尽量 GT+ParallelForEachEntityChunk，移出 UObject 操作的收益比代价高”】
  快照化设计要点（槽池快照方案——比“逐星预查询”更优）：
   ① GT 预快照（O(轨数) 次数组拷贝）：每轨拷贝【槽位置数组+槽句柄数组】到本地快照容器
      （TMap<FName, FSlotSnapshot>——纯数据，总几十 KB/帧，可忽略；比 O(星数) 次查询更省）
   ② ParallelForEachEntityChunk：每实体读 OrbitName+SlotClaimHandle → 在快照里解析
      （IndexOfByKey 变纯数据操作）→ 算显示位置 → 局部缓冲 → 锁合并（不依赖两次遍历顺序一致性）
   ③ 并行区外：批提交 BatchUpdateInstancesTransforms（不变）
  收益边界：GT 侧成本≈现状或更省（O(轨数) vs O(星数) 访问）；并行=位置计算+收集；
  当前规模微小、随规模放大——本质是模式统一收益（框架级）为主
· Slot/Plan：无实体级循环（单次调用）——不适用

登记：【✅ 编译通过（10-07）】——Movement（L61 换 Parallel）+ Render（两段式：
  GT 预快照 L33 → 并行收集 L67 → 批提交 L120）+ .h 注释；3 文件已 reindex；断点地图已重校。
  实施偏差记录：实际采用【逐星预查询快照】（TMap<EntityHandle, FVector>，含 bOverrideLocation 过滤）
  而非上述“槽池快照”——原因：零接口改动（不必为 SmartObjectManager 新增按轨快照接口）
  + GT 工作量与现状持平（O(星数) 查询反正都要做）；两方案对比：槽池快照 O(轨数) 访问更省但需新接口 /
  逐星快照单文件闭环。若未来 N8（槽池自建）落地，可顺势改为槽池快照（更自然）。
```
